## Google Sign-In: one follow-up left, not blocking

Google Sign-In works end-to-end on Android, confirmed via actual beta
testing on a real device (not just the emulator, and not just
`flutter analyze`/`flutter test` — see the note below on why that
distinction turned out to matter). The Google provider is enabled in
Firebase Console, both the debug **and release** keystore SHA-1
fingerprints are registered, and `android/app/google-services.json`
carries both OAuth client entries.

**A real bug shipped in early beta builds (beta1–beta3) and is worth
recording, not glossing over**: registering the SHA-1 fingerprints
was necessary but not sufficient. A real device attempt failed with
`GoogleSignInExceptionCode.clientConfigurationError` —
"serverClientId must be provided on Android" — because
`google_sign_in`'s Android implementation is supposed to auto-detect
this from `google-services.json`'s native-generated
`default_web_client_id` resource, and that fallback wasn't happening
in this build. Fixed by passing the web-client OAuth ID (`client_type:
3` in `google-services.json`) explicitly to
`GoogleSignIn.instance.initialize()` in `auth_remote_datasource.dart`.
**This is exactly the kind of bug `flutter analyze`/`flutter test`
structurally cannot catch** — nothing in this project's test suite
exercises the real native sign-in path, and nothing can without a
real device. One thing still to do:

- Add the iOS side: enable the Google provider's iOS config, download
  `GoogleService-Info.plist` with its `REVERSED_CLIENT_ID`, and add the
  matching URL scheme to `Info.plist`. Deferred because this project
  has never been tested on an iOS device/simulator — see the iOS
  groundwork section below for the full, precise checklist.

## iOS: what's actually there, and the exact steps left

Nothing about this project has ever been built or run on iOS (no Mac in
this dev environment). Audited the current `ios/Runner` state directly
rather than assuming a bare scaffold — here's exactly what exists and
what's missing:

- **`ios/Runner/GoogleService-Info.plist` already exists** and is a
  real file (has a genuine `GOOGLE_APP_ID`/`API_KEY`/`PROJECT_ID` for
  `cashly-lao`, bundle ID `com.cashlylao.app`) — but it has **no
  `CLIENT_ID`/`REVERSED_CLIENT_ID` keys**, which a Firebase-generated
  plist only includes once Google Sign-In's iOS OAuth client has been
  created for this app. `IS_SIGNIN_ENABLED` is `true`, but that flag
  reflects Firebase Auth generally, not that an iOS OAuth client
  exists — it doesn't yet.
- **`ios/Runner/Info.plist` has no `CFBundleURLTypes`** entry, so
  there's no URL scheme registered for Google Sign-In's redirect to
  land on. `google_sign_in`'s iOS setup requires one, keyed to the
  `REVERSED_CLIENT_ID` above.
- **No `ios/Podfile` yet** — expected, since it's generated by `pod
  install`/`flutter build ios`, and CocoaPods can't run outside macOS.
  Nothing to fix here, just means dependency resolution itself is
  still completely unverified on iOS.

Steps to actually close this, in order, all requiring either Firebase
Console/Google Cloud Console access or a Mac — none of them are
reachable from this environment:

1. In Google Cloud Console (same `cashly-lao` project) → **APIs &
   Services → Credentials**, create an **iOS** OAuth 2.0 Client ID for
   bundle ID `com.cashlylao.app` (or confirm Firebase Console's
   Authentication → Sign-in method → Google → the iOS app is already
   associated, which auto-creates it).
2. Re-download `GoogleService-Info.plist` from Firebase Console
   (Project settings → your iOS app) — it will now include
   `CLIENT_ID`/`REVERSED_CLIENT_ID` — and replace
   `ios/Runner/GoogleService-Info.plist` with it.
3. Add a `CFBundleURLTypes` entry to `ios/Runner/Info.plist` with that
   `REVERSED_CLIENT_ID` as the URL scheme (the standard `google_sign_in`
   iOS setup block, documented in the package's own README). Left
   undone here deliberately rather than added with a placeholder value
   — a fake URL scheme would silently look "wired up" while being
   inert, which is exactly the kind of no-op the project avoids.
4. On a Mac: `flutter build ios` (or open in Xcode) to generate the
   `Podfile`/run `pod install`, resolve signing (a real Apple Developer
   account + provisioning profile — separate from Android's keystore
   entirely), and do a first real device/simulator run.

## Premium / monetization

Sprint 9 originally shipped a Premium feature gating Reports behind a
demo toggle (`activatePremium()`/`deactivatePremium()`, no real payment
behind them — see `PROJECT_PROGRESS.md` Sprint 9). It was **removed
ahead of the v1 launch**: a demo "purchase" flow with no real IAP behind
it is a genuine App Store review risk (guideline 3.1.1 requires real IAP
for unlockable digital content), so Reports ships free for everyone in
v1 instead. If monetization returns in a later release, build it fresh
rather than resurrecting the removed code — the client-side toggle
wasn't the right shape for it anyway:

- **Real in-app-purchase integration.** Add the `in_app_purchase`
  package, configure products in App Store Connect / Google Play
  Console, and validate purchases server-side (a Cloud Function
  verifying the receipt) before granting any entitlement flag.
- **Validate entitlement writes server-side from day one.** Don't let a
  signed-in client set its own entitlement field directly — that was the
  real, documented gap in the removed `isPremium` design. Grant it only
  via a Cloud Function using the Admin SDK after verifying a purchase
  receipt.
- **Restore purchases** flow for a user who reinstalls or switches
  devices.

## Security & data

- **Deep-linkable edit routes.** Account/Category/Budget/Transaction edit
  screens currently receive the entity via GoRouter's `extra`, which only
  works when navigating from within the app. A cold deep link (e.g. from
  a notification or shared URL) to an edit route would need the screen to
  fetch by ID instead. Not a bug today since nothing generates such
  links, but worth closing before a web deployment relies on shareable
  URLs.
- **Revisit Firestore composite indexes** if query patterns change (e.g.
  filtering transactions by category *and* date range in one query would
  need one — today's queries are all single-field filters/sorts and need
  none).
- **Pagination for large histories.** Accounts and Categories currently
  fetch their entire collection and filter client-side; Transactions
  already scopes by month. Fine at a personal-finance app's realistic
  data volumes, but worth revisiting if a power user's transaction count
  grows into the thousands.

## Localization & accessibility

- **Lao-language localization is now string-complete and on-device
  verified.** Every screen (Auth, Dashboard, Accounts, Transactions,
  Categories, Budget, Reports, Settings, Profile, plus the bottom-nav
  shell and the shared icon/color picker fields) is extracted into
  `app_en.arb`/`app_lo.arb`, and the shared `Validators` utility
  (`core/utils/validators.dart`) was migrated to take `BuildContext` and
  pull its error strings from `AppLocalizations` too (a deliberate
  breaking-signature change — every call site across the app was
  updated). `flutter analyze` (0 issues) and `flutter test` (all green)
  both pass. The Lao locale was forced on a real emulator (owner signed
  in manually with Google to avoid the autofill risk noted below) and
  every screen was swept and screenshotted — this also caught and fixed
  a real bug found only by doing this on-device: `DateFormat` calls
  (month/date labels everywhere) were reading from `Intl.defaultLocale`,
  a separate global from `MaterialApp`'s `locale:`, which nothing ever
  set — so dates silently stayed English even with the rest of a screen
  in Lao. Fixed in `lib/app.dart` by syncing `Intl.defaultLocale` to the
  resolved locale.
  - **Native-speaker review** is the one remaining item. Every Lao
    string added across this whole effort is a draft, not written by a
    certified translator — have a native Lao speaker review
    `lib/l10n/app_lo.arb` end-to-end before shipping.
  - **Savings Goals (Stage 8)'s ~44 new keys are now translated
    (draft)**, closing the gap where it had shipped English-only —
    `app_lo.arb` previously had zero entries for this feature; on-device
    testing confirmed the feature gracefully fell back to English for
    them in the meantime (no crash, no broken layout), and that fallback
    behavior itself is worth keeping in mind as a safety net for any
    future feature that ships translation-incomplete. These new strings
    carry the same "draft, not certified" status as the rest of the
    file, so they're covered by the native-speaker review above, not a
    separate step — including the vocabulary choices made for concepts
    with no prior precedent in the app (translating "contribute"/
    "contribution" as ຝາກເງິນ/ການຝາກເງິນ, "deposit money," rather than a
    more literal but stiffer loan-word for "contribution," and "goal" as
    ເປົ້າໝາຍ, reusing the full ເປົ້າໝາຍການເກັບເງິນ "savings goal" only
    where the English itself spells it out rather than shortening to
    just "goal") — a native speaker should sanity-check those choices
    specifically, not just proofread grammar.
  - **Four real bugs caught only by on-device testing**, during Stage 8's
    verification pass: (1) an app-wide theme-construction crash on cold
    start — `ThemeData.light()/.dark().textTheme` returns every field
    with a null `fontSize` when built outside a `BuildContext` on Flutter
    3.44.6, which `AppTheme._buildTheme` then fed into
    `.apply(fontSizeFactor: ...)`, tripping a Flutter assertion. Fixed by
    explicitly rebuilding the Material 3 typography merge
    (`Typography.material2021(...).englishLike.merge(...black`/`.white)`)
    instead of relying on the implicit one `MaterialApp` normally does.
    Bundled Manrope + Plus Jakarta Sans as local font assets in the same
    pass (matching the existing Noto Sans Lao pattern), removing the
    `google_fonts` dependency entirely. (2) A `DropdownButtonFormField`
    orphan-value crash on goal creation — fixed with a
    `_withOrphanFallback` helper in `savings_goal_form_screen.dart`,
    mirroring the existing pattern already used in
    `transaction_form_screen.dart`. (3) Goal Detail's "Account activity"
    section could get stuck loading forever: `_goalActivityRange()` in
    `savings_goal_providers.dart` keyed a non-`autoDispose`
    `StreamProvider.family` off a millisecond-precision `DateTime.now()`,
    so every emission minted a brand-new, never-disposed Firestore
    listener instead of reusing one — if the one instance actually in use
    died (e.g. a network drop), nothing was left watching it to ever
    retry. Fixed by truncating to day granularity, the same stable-key
    approach `report_providers.dart` already uses. (4) Deleting a goal
    from Detail's menu left the screen permanently stranded on a "this
    goal no longer exists" error instead of returning to the list, even
    though the delete had genuinely succeeded —
    `savingsGoalControllerProvider`'s `.autoDispose` notifier had nothing
    keeping it alive from that call site (unlike the form screen, which
    watches it for its Save button's loading state), so it got disposed
    mid-flight the instant the goal's disappearance flipped Detail to its
    error view, throwing "Ref used after dispose" instead of ever letting
    `context.pop()` run. Fixed in `savings_goal_controller.dart`'s shared
    `_run` helper by guarding each `state = ...` write with
    `if (ref.mounted)`, Riverpod's own recommended fix for this race.
    All four confirmed fixed via `flutter analyze`/`flutter test` plus a
    full on-device re-pass (create/edit/archive/unarchive/delete/
    contribute/completion-celebration all exercised end-to-end). See
    `ROADMAP.md`'s Stage 8 entry for complete detail and for what's still
    genuinely unverified (auto-contribution reminder notifications firing,
    dark mode, Lao locale).
  - **Android autofill risk during sign-in, for future reference.** An
    earlier on-device sign-in attempt this project was hit by Android's
    autofill/credential service silently substituting different account
    details into the registration form and submitting it before it
    could be caught, creating an unintended real Firebase user that had
    to be cleaned up manually. Stages 3 and 4 skipped on-device
    verification for this reason; Stage 5 completed it by having the
    project owner drive sign-in manually on the emulator rather than
    letting an agent type into auth forms.
  - **Accessibility audit** — screen-reader labels, color-contrast check
